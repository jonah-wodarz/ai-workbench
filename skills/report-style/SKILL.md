# Report Style

The reader gets the point from the first lines and finds any detail by scanning. The project's own doc conventions override this skill where they differ.

## Steps

1. **Lead with the result**: the answer, conclusion or decision needed, in one to three lines. State a required action first ("Decision needed: X").
2. **Order the support by importance**, not by the order the work happened. Leave the work's steps out of the text.
3. **Fix the terms**: one term per concept across text, headings and tables. Define an ambiguous or unfamiliar term by what it does, at first use ("doclint (the script that checks the docs against the conventions)"), then use the bare term.
4. **Refer by name, IDs inside**: "the precision rule (ARC-R13)".
5. **Write short sentences**: one idea each, active voice, verbs over noun constructions. German: verbal style ("prüfen", not "Durchführung einer Prüfung"), no Schachtelsätze, technical terms stay English.
6. **Use a visual when it carries the content**, then state its takeaway in one sentence.
7. **Place uncertainty next to the claim** it affects ("unverified", "assumption").
8. **Check** that the reader could stop after three lines and know the result, and that every sentence reads correctly the first time.

| Content | Visual |
|---|---|
| 3+ items compared on shared attributes | Table |
| Process, flow, dependencies | Diagram or numbered list |
| Numbers over time or categories | Chart |
| Status of many items | Table with a status column |

A visual needs headers, units and a caption where the meaning is not obvious.

## Summary after multi-step work

1. **Outcome**: what exists or was found, one to three lines.
2. **Decisions needed / open points**, only if any.
3. **Details**: the essentials, usually a table; point to files for the rest.
4. **Next steps**: concrete, one or more.

Headings are labels; bullets for parallel items, numbers for sequences, prose for reasoning.
